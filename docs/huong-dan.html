archctl 0.1.1 · viết 16/11/2026, cập nhật 18/11/2026

archctl là gì, và cách dùng nó từng bước

Tóm tắt

archctl là một chương trình dòng lệnh đọc một file luật kiến trúc do bạn viết, rồi kiểm xem mã nguồn có đi ngược luật đó không. Nó sinh ra để dùng cạnh một agent lập trình (Claude Code, Codex): agent viết mã, archctl là người gác cổng. Trang này đưa bạn đi qua 11 bước, mỗi bước có lệnh để gõ và kết quả thật tôi đã chạy trên bản sao dự án mẫu examples/shop; bước 10 là vẽ và sửa luật ngay trên sơ đồ trong trình duyệt. Phần cuối dạy cách viết file luật: mỗi loại khai báo có một câu nói nó để làm gì và một ví dụ đã qua bộ đọc của archctl. Bản archctl mới nhất đã nằm sẵn trong máy bạn, không cần cài thêm. Không có việc nào bạn cần chốt; đây là trang đọc và làm theo.

Từ gốc

Hệ thống đang làm gì

Khi để một agent tự viết mã, kiến trúc dễ trôi: hôm nay module kho hàng chỉ gọi module thông báo, tuần sau agent thấy tiện nên cho nó gọi thẳng module thanh toán. Không ai thấy vì mã vẫn chạy. archctl chặn việc này như sau. Bạn viết ra một file nhỏ (.arch/system.arch) nói "ai được gọi ai". archctl đọc mã, lần ra mọi chỗ một module nạp module khác, và so với file đó. Chỗ nào lệch thì in ra tên file, số dòng và cách sửa.

Hình: nét liền là luồng chạy; nét đứt là luật bạn viết, archctl đọc. Vi phạm quay lại agent; agent sửa mã hoặc propose một luật mới cho bạn duyệt.

Vấn đề hôm nay

Nếu bạn chỉ dặn agent "đừng để kho hàng gọi thanh toán" bằng lời, nó có thể quên, hoặc làm sai mà vẫn báo xong. Luật nằm trong file thì máy kiểm được, mỗi lần agent sửa file, và nhắc nó ngay trong lúc làm. Khi luật thật sự sai (kho hàng cần gọi thanh toán), agent cũng cần một đường hợp lệ để xin đổi luật, nếu không nó sẽ lách luật hoặc kẹt mãi. Đường đó là lệnh propose ở bước 7.

Cần biết trước

  1. Component (thành phần): một khối mã gắn với một nhóm đường dẫn. Ví dụ: component Stock at src/stock/** nghĩa là mọi file dưới src/stock/ là khối "Stock". Cần để hiểu: mọi luật khác đều nói về component.
  2. allow và deny: allow Order -> Stock, Payment cho Order gọi Stock và Payment. deny * -> Stripe except Payment cấm mọi component trừ Payment đụng tới thư viện stripe. Cần để hiểu: các vi phạm ở bước 3. Một component đã có allow mà gọi sang chỗ không được liệt kê là vi phạm.
  3. Trạng thái #draft, #proposed, #accepted, #locked: #draft là bản nháp và #proposed là đang đề xuất, cả hai chưa có hiệu lực; #accepted là đã duyệt, đang được kiểm; #locked cũng được kiểm, và giao diện sơ đồ hỏi lại trước khi cho sửa. Cần để hiểu: bước 8 (áp lên dự án có sẵn) và bước 10.
  4. Người ghi và dấu @human / @ai: mỗi dòng luật ghi ai đặt ra nó. Agent không được ghi system.arch; nó chỉ ghi proposals.arch. Cần để hiểu: bước 7.
  5. Mã thoát: số mà lệnh trả về cho shell. 0 là sạch, 1 là có vi phạm, 3 là có đề xuất đang chờ bạn. Cần để hiểu: vì sao CI (hệ thống tự chạy kiểm sau mỗi lần đẩy mã) biết đỏ hay xanh.

Thuật ngữ

.arch/
Thư mục ở gốc dự án chứa mọi thứ của archctl. Gốc dự án là thư mục gần nhất đi lên có .arch/system.arch.
system.arch
File luật. Chỉ người sửa.
proposals.arch
File đề xuất. Chỉ agent ghi, qua propose và block.
decisions.md
Nhật ký mọi lần bạn duyệt hay từ chối, kèm lý do. Agent đọc nó để không đề xuất lại thứ đã bị từ chối.
.state
File máy tự ghi: nhớ mỗi vi phạm đã gặp mấy lần. Không đưa vào git.
hook
Lệnh mà Claude Code tự chạy sau mỗi lần agent sửa file. archctl dùng nó để nhắc agent ngay lúc vừa vi phạm.
baseline
Danh sách vi phạm có sẵn từ trước, được tha để dự án cũ có thể bật archctl mà không phải sửa hàng trăm chỗ cùng lúc.
biên nhận (verify)
Kết quả một lệnh kiểm do bạn khai báo trong luật (ví dụ chạy test), ghi lại sau khi nó chạy thật.
HEAD
Tên của commit mới nhất trong git. archctl diff so luật hiện tại với nó.
CI
Hệ thống tự chạy kiểm sau mỗi lần đẩy mã lên GitHub. Nằm ngoài tầm với của agent.
Mermaid
Định dạng chữ để vẽ sơ đồ; GitHub tự vẽ thành hình.

Hướng dẫn từng bước

Làm theo thứ tự. Mọi lệnh dưới đây chạy trong một thư mục bản sao, nên không làm hỏng repo thật. Kết quả hiện ra là kết quả thật của lần chạy tôi làm sáng nay; ngày tháng và mã băm của bạn sẽ khác.

1 Kiểm máy bạn có archctl

Gõ 
archctl
Bạn sẽ thấy 
archctl 0.1.1 — sơ đồ kiến trúc là luật

Bắt đầu:
  archctl init [--from-code] [--no-hooks] Dựng .arch/ cho dự án
  archctl baseline                        Tha vi phạm có sẵn, chỉ chặn cái mới
…

Vì sao Chương trình nằm ở ~/.cargo/bin/archctl, do bạn dựng từ repo này. Nếu một ngày lệnh báo "không tìm thấy", dựng lại bằng cargo install --locked --path crates/archctl trong repo.

2 Dựng một dự án mẫu để thử

Dự án mẫu shop là một cửa hàng TypeScript nhỏ, cố ý cài sẵn vi phạm. Chép nó ra chỗ khác để mọi thao tác sau không đụng vào repo.

Gõ 
mkdir -p ~/archctl-thu
cp -R /Users/macos/Documents/Claude/archctl/examples/shop ~/archctl-thu/shop
cd ~/archctl-thu/shop
rm -f .arch/.state
ls -a .arch
Bạn sẽ thấy 
.   ..   system.arch

Vì sao Dự án mẫu đi kèm một .state cũ ghi "đã gặp lại 17 lần"; xóa nó để bộ đếm của bạn bắt đầu từ 0 như dự án thật. Chỉ mình system.arch là file luật.

3 Đọc file luật rồi chạy check

Mở .arch/system.arch. Phần quan trọng nhất là bảy dòng này:

component Web      at src/web/**       @human #locked
component Stock    at src/stock/**     @human #accepted
component Payment  at src/payment/**   @human #accepted
external  Stripe   at "stripe"         @human #accepted

allow Web     -> Order, User
allow Stock   -> Notify
deny  * -> Stripe   except Payment

Đọc thành lời: Stock chỉ được gọi Notify. Chỉ Payment được dùng thư viện stripe. (Từng loại khai báo được dạy kỹ ở phần Cú pháp system.arch cuối trang.) Giờ cho archctl kiểm:

Gõ 
archctl check
Bạn sẽ thấy (rút gọn) 
kiến trúc cc0e13c3… · 7 file quét (7 TypeScript) · 4/6 component trong diện kiểm

✗ VI PHẠM  Stock -> Payment  (không được phép, #accepted)
  src/stock/reserve.ts:5  import '../payment/charge'
  luật: không có allow nào cho Stock -> Payment
  → Stock chỉ được gọi: Notify

✗ VI PHẠM  Web -> Stripe  (bị cấm, #accepted)
  src/web/checkout-page.ts:5  import 'stripe'
  luật: deny * -> Stripe except Payment
  → gọi Payment thay vì truy cập thẳng Stripe

✗ VI PHẠM  Web -> Timeout  (lọt ra ngoài vùng, #accepted)
  src/web/checkout-page.ts:12  dùng `Timeout` (2 lần trong file)
…
⚠ KHAI BÁO LẠC HẬU  bước của flow PlaceOrder `updateAnalytics`
⚠ CHƯA PHÂN GIẢI  '../shared/cart-types'
⚠ CHƯA CHỨNG MINH  cách kiểm `contract_test` — chưa chạy lần nào

3 vi phạm mới, 11 cảnh báo

Cách đọc Dấu ✗ là vi phạm luật đang có hiệu lực: phải sửa. Dấu ⚠ là cảnh báo, chưa làm lệnh thất bại. "Khai báo lạc hậu" nghĩa là luật nhắc tới một bước tên updateAnalytics mà mã không có; sơ đồ đang nói dối. "Chưa phân giải" nghĩa là archctl không tìm ra file mà dòng import trỏ tới. Dòng "→" là cách sửa gợi ý. Lệnh trả mã thoát 1 vì có vi phạm.

Lần đầu bạn có thể thấy thêm một dòng "Kiến trúc đã thay đổi kể từ lần kiểm trước". Đó là archctl nhắc bạn (hoặc agent) đọc lại file luật khi hash của nó đổi; không phải lỗi.

4 Xem archctl đọc mã ra sao

Khi một vi phạm làm bạn ngạc nhiên, hỏi thẳng archctl nó thấy gì trong file đó.

Gõ 
archctl scan src/stock/reserve.ts
Bạn sẽ thấy 
src/stock/reserve.ts (TypeScript)
      1  ../notify/send  → src/notify/send.ts
      5  ../payment/charge  → src/payment/charge.ts

Vì sao Dòng 5 chính là nguồn của vi phạm ở bước 3: file kho hàng nạp thẳng file thanh toán. scan không cần .arch/, nên dùng được ở bất kỳ thư mục mã nào để xem archctl hiểu gì. Thêm --json nếu muốn máy khác đọc.

5 Để ý bộ đếm lần thử

Chạy archctl check thêm lần nữa, rồi lần nữa.

Bạn sẽ thấy (lần thứ hai) 
✗ VI PHẠM  Stock -> Payment  (không được phép, #accepted)
  src/stock/reserve.ts:5  import '../payment/charge'
  …
  (lần thứ 2)

Vì sao Vi phạm chưa sửa mà gặp lại thì bộ đếm tăng. Tới lần thứ 3, archctl in thêm đúng lệnh agent nên chạy ("! đã gặp lại 3 lần — không sửa được thì dừng lại và: archctl propose …"). Đây là cách nó chặn agent cố sửa mãi một chỗ mà không được.

6 Sửa vi phạm thật

Cách mặc định luôn là sửa mã cho đúng luật. Với vi phạm Stock -> Payment, hướng đúng là bỏ import ở src/stock/reserve.ts dòng 5, để Order (component được phép gọi cả Stock lẫn Payment) điều phối. Sau mỗi lần sửa:

Gõ 
archctl check src/stock/reserve.ts

Vì sao Đưa tên file vào thì kiểm cực nhanh (khoảng 11 mili giây trên 2000 file TypeScript, theo README), nên agent chạy được sau mỗi lần sửa. Sửa xong, vi phạm biến mất và bộ đếm của nó về 0.

7 Khi luật sai: agent đề xuất, bạn quyết

Giả sử bạn thấy kho hàng thật sự cần hỏi thanh toán. Agent không được tự sửa system.arch. Nó chạy lệnh dưới và dừng việc đó lại.

Gõ (vai agent) 
archctl propose 'allow Stock -> Payment' --reason "reserve cần kiểm hạn mức thanh toán"
Bạn sẽ thấy 
Đã ghi đề xuất `p-6938d093fae0d371`: allow Stock -> Payment
→ DỪNG phần việc này lại và làm việc khác. Chờ người quyết định.

Mã thoát là 3. Giờ vai bạn: xem danh sách chờ.

Gõ (vai bạn) 
archctl proposals
Bạn sẽ thấy 
ĐỀ XUẤT p-6938d093fae0d371  allow Stock -> Payment
  lý do: reserve cần kiểm hạn mức thanh toán
1 đang chờ. Duyệt: archctl accept <id> --reason "..." · Từ chối: archctl reject <id> --reason "..."

Bạn có hai lựa chọn, và --reason là bắt buộc cho cả hai.

Từ chối 
archctl reject p-6938d093fae0d371 --reason "Stock không được biết Payment. Để Order gọi Payment rồi truyền kết quả cho Stock."
Hoặc duyệt 
archctl accept p-6938d093fae0d371 --reason "Chỉ đọc hạn mức, an toàn"

Khi duyệt, archctl tự thêm dòng allow Stock -> Payment @ai #accepted vào cuối system.arch. Khi từ chối, nó ghi vào decisions.md. Bạn thử để agent đề xuất lại đúng luật đó:

Bạn sẽ thấy 
Đề xuất này đã bị từ chối ngày 2026-11-16 bởi tdHuy22.
Lý do: Stock không được biết Payment. Để Order gọi Payment rồi truyền kết quả cho Stock.

→ Đừng đề xuất lại. Tìm hướng khác, hoặc hỏi người dùng.

Vì sao Agent không nhớ gì giữa các phiên. Nếu không có decisions.md, ngày mai nó đề xuất lại y hệt. Viết lại luật với khoảng trắng khác cũng bị nhận ra, vì mã nhận diện được tính trên nội dung đã chuẩn hóa. Lệnh archctl block --on '<luật>' --reason "…" là anh em của propose: dùng khi đã có một luật deny chặn agent và nó kẹt.

8 Áp lên dự án đã có mã: init --from-code và baseline

Dự án thật không có sẵn file luật và có thể có hàng trăm vi phạm cũ. Hai lệnh giải đúng hai vấn đề đó. Thử trên một thư mục mới chỉ có mã:

Gõ 
mkdir ~/archctl-thu/shop2 && cp -R ~/archctl-thu/shop/src ~/archctl-thu/shop2/src
cd ~/archctl-thu/shop2 && git init -q
archctl init --from-code --no-hooks
Bạn sẽ thấy 
Đã đọc 7 file (7 TypeScript) · gốc mã nguồn: src
Dựng được 7 component và 7 quan hệ, tất cả ở `#draft`.

  tạo  .arch/system.arch
  tạo  .arch/proposals.arch
  tạo  .arch/decisions.md
  tạo  .arch/ARCHITECTURE.md
  sửa  AGENTS.md
  sửa  CLAUDE.md
  sửa  .gitignore

Nó chia mỗi thư mục con của src/ thành một component và ghi lại mọi quan hệ import có thật thành allow, tất cả ở #draft. Chạy archctl check lúc này cho "0/7 component trong diện kiểm": chưa luật nào có hiệu lực, vì file đang mô tả hiện trạng chứ chưa phải thiết kế. Việc của bạn:

  1. Mở .arch/system.arch. Xóa quan hệ không nên tồn tại (ví dụ allow Stock -> Payment).
  2. Đổi @ai #draft thành @human #accepted ở phần bạn chắc. Component nào có allow đang có hiệu lực thì bắt đầu bị kiểm; phần còn lại tạm để yên.
  3. Chạy archctl check. Nếu còn quá nhiều vi phạm cũ, chạy archctl baseline để tha chúng.
Thử baseline trên bản shop ở bước 2 
cd ~/archctl-thu/shop
archctl baseline
Bạn sẽ thấy 
Đã ghi .arch/baseline: 3 vi phạm được tha.

Vì sao File .arch/baseline liệt kê ba vi phạm theo dạng Stock->Payment|src/stock/reserve.ts|../payment/charge. Chạy check lại: ba vi phạm cũ không còn bị báo, mã thoát về 0, nhưng một import sai mới sẽ bị chặn. Thêm import '../web/checkout-page' vào cuối src/stock/reserve.ts và chạy archctl check src/stock/reserve.ts: bạn thấy dòng "✗ vi phạm Stock -> Web" và mã thoát 1. Lưu ý check --strict vẫn trả 1 sau baseline vì các cảnh báo "chưa chứng minh" còn đó; đó là lý do CI phải chạy verify trước (bước 11). Sửa được một cái cũ thì chạy baseline lại để siết; đã bỏ khỏi danh sách thì không quay lại được.

Lưu ý: không dùng --no-hooks thì init còn ghi hook vào .claude/settings.json của dự án (bước 9). Tôi thêm cờ đó ở đây để thử không đổi cấu hình Claude Code nào cả.

9 Gắn vào Claude Code để nó nhắc agent tự động

Chạy archctl init (không có --no-hooks) sinh ra đoạn này trong .claude/settings.json:

{
  "matcher": "Edit|Write|MultiEdit|Bash",
  "hooks": [{ "type": "command", "command": "archctl check --hook", "timeout": 30 }]
}

Nghĩa là sau mỗi lần Claude Code sửa file hay chạy lệnh shell, nó chạy archctl check --hook. Lệnh này đọc thông tin lần sửa từ Claude Code, kiểm đúng file đó, rồi đưa vi phạm vào ngữ cảnh mà model đọc được. Thử tự tay, giả làm Claude Code vừa sửa reserve.ts (thay /đường/dẫn/shop bằng đường dẫn thật của bạn):

Gõ 
echo '{"tool_name":"Edit","tool_input":{"file_path":"/đường/dẫn/shop/src/stock/reserve.ts"}}' | archctl check --hook
Bạn sẽ thấy (rút gọn, một dòng JSON) 
{"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"archctl: vi phạm luật kiến trúc … ✗ VI PHẠM  Stock -> Web …"}}

Vì sao Lệnh luôn thoát 0 và không in gì nếu không có vi phạm mới. Lý do thiết kế: Claude Code chỉ đưa vi phạm cho model khi hook trả JSON theo dạng này; một lệnh thoát 1 bị coi là lỗi không chặn và model không bao giờ thấy. README ghi: dự án init bằng bản 0.1.1 trở về trước thì hook cũ vô hiệu, phải sửa tay hai dòng đó.

10 Vẽ và sửa luật trên sơ đồ: archctl serve

archctl serve mở một máy chủ chỉ máy bạn thấy, rồi in ra địa chỉ để mở trong trình duyệt. Mọi thứ trong system.arch đều thêm, sửa, xoá được ngay trên sơ đồ, không phải mở file. Sơ đồ tự cập nhật trong khoảng nửa giây khi agent sửa mã hay luật.

Gõ (trong ~/archctl-thu/shop) 
archctl serve --port 4123
Bạn sẽ thấy (khoá của bạn khác) 
archctl serve · http://127.0.0.1:4123/?k=f93986017075681d53133f31f37c8b95

Mở đúng địa chỉ có ?k=…. Phần sau ?k= là khoá phiên: một chuỗi ngẫu nhiên sinh mỗi lần chạy serve, chỉ in ra màn hình của bạn, không ghi vào file. Thiếu khoá thì máy chủ từ chối mọi yêu cầu đọc và ghi. Lý do: agent chạy trên cùng máy, không có khoá thì một lệnh curl là nó tự duyệt được đề xuất của chính nó.

11 Xuất hình, chạy kiểm thật, và CI

Xuất ảnh tĩnh. archctl export in sơ đồ Mermaid để dán vào mô tả pull request hay file .md; thêm --violations thì vi phạm hiện thành mũi tên đậm đỏ ("Stock ==>|vi phạm| Payment"); --out sodo.md ghi ra file mà GitHub tự vẽ.

Chạy kiểm thật. Dòng verify trong luật gắn tên với một lệnh shell. archctl verify chạy các lệnh đó và ghi biên nhận. Thử trên chính repo archctl, vì nó có luật verify no_deps chỉ đếm gói trong Cargo.lock:

Gõ (trong thư mục repo archctl) 
cd /Users/macos/Documents/Claude/archctl
archctl verify no_deps
Bạn sẽ thấy 
▸ no_deps  test "$(grep -c '^\[\[package\]\]' Cargo.lock)" -eq 2
  đạt · 0.0 giây

1/1 đạt · biên nhận ghi vào .arch/.verified

Đây là lệnh duy nhất của archctl chạy lệnh shell, và chỉ khi chính bạn gõ nó. Mỗi lệnh có trần 1800 giây (đổi bằng --timeout). Biên nhận không vào git.

Trong CI, thứ tự này quan trọng:

- run: archctl verify
- run: archctl check --strict

--strict biến mọi cảnh báo, cả "chưa chứng minh", thành vi phạm; vì vậy phải verify trước để có biên nhận. CI là chỗ agent không với tới, nên là nơi cưỡng chế thật. Trên máy bạn, agent chạy được shell thì vẫn ghi đè được file luật; README gọi đây là "lan can, không phải hàng rào an ninh". Muốn chắc hơn, khóa .arch/** bằng CODEOWNERS (file GitHub chỉ định ai duyệt thay đổi nào).

So với bản trước. archctl diff so luật hiện tại với HEAD và tách thay đổi kiến trúc thật khỏi thay đổi chỉ xê dịch chữ, để bạn biết đọc kỹ chỗ nào. Trên repo archctl hiện ra "không đổi so với HEAD".

Ba ví dụ làm lại từ đầu

Nếu bạn muốn thử không cần đọc trang, ba tình huống sau là ba cách dùng thường gặp, mỗi cái chạy trên bản shop bạn vừa chép.

Ví dụ 1 · Ca thường gặp: agent vừa viết vi phạm

Tình huống: bạn nhờ agent "cho kho hàng kiểm hạn mức thanh toán". Nó thêm import '../payment/charge' vào src/stock/reserve.ts.

archctl check src/stock/reserve.ts
✗ VI PHẠM  Stock -> Payment  (không được phép, #accepted)
  src/stock/reserve.ts:5  import '../payment/charge'

Hôm nay không có archctl thì mã chạy bình thường và không ai biết. Với hook ở bước 9, agent thấy dòng trên ngay sau lần sửa và tự đưa việc gọi thanh toán về Order. Vì sao quan trọng: lỗi bị bắt ở 11 mili giây, trước khi nó thành thói quen của cả dự án.

Ví dụ 2 · Ca biên: sơ đồ nói dối vì mã đã đổi

Tình huống: luật flow PlaceOrder liệt kê bước updateAnalytics, nhưng agent đã xóa hàm đó khi dọn mã. Mã không vi phạm import nào, nên chẳng ai để ý.

⚠ KHAI BÁO LẠC HẬU  bước của flow PlaceOrder `updateAnalytics`
  .arch/system.arch:22  — `updateAnalytics` không có trong mã — sửa mã, hoặc sửa khai báo

Đây không phải lỗi import mà là sự lệch giữa sơ đồ và mã. archctl bắt nó vì agent hay đổi tên một bước rồi để sơ đồ cũ nằm đó. Ở chế độ --strict (CI), cảnh báo này làm đỏ.

Ví dụ 3 · Ca hỏng: agent bị kẹt và bạn từ chối đề xuất

Tình huống: agent sửa ba lần vẫn không hợp luật (vì luật thật sự cản đúng việc được giao). Ở lần thứ 3 archctl in lệnh propose. Agent chạy lệnh, dừng, và chờ. Bạn từ chối kèm lý do ở bước 7.

Đề xuất này đã bị từ chối ngày 2026-11-16 bởi tdHuy22.
→ Đừng đề xuất lại. Tìm hướng khác, hoặc hỏi người dùng.

Ngày mai, phiên mới của agent không nhớ gì, nhưng decisions.md còn đó. Nó không thể lách bằng cách đề xuất lại, cũng không có quyền ghi system.arch. Hạn chế thật: nếu agent chạy được shell, nó vẫn có thể sửa file luật bằng tay. Trên máy này, bộ công cụ agent-stack của bạn có một hook chặn agent sửa system.arch và chạy archctl baseline (tôi đã gặp chính hook đó khi chuẩn bị trang này); ngoài ra chỉ CI và CODEOWNERS mới chắc.

Cú pháp system.arch cho người mới

File luật là chữ thường, mỗi khai báo bắt đầu bằng một từ khoá. Có 14 từ khoá; gõ từ nào khác thì archctl báo "từ khoá không nhận ra". Mọi ví dụ dưới đây đã chạy qua archctl parse <file> (lệnh chỉ đọc và soát cú pháp, không quét mã) và cho "không có lỗi, không có cảnh báo", trừ hai ví dụ cố ý sai ở cuối.

Luật chung cho mọi dòng

  • Một khai báo một dòng. Riêng flow, contract, boundary kết thúc dòng đầu bằng dấu : và có thân khối: các dòng lùi vào bên dưới. Dòng lùi sâu hơn một khoá là phần tiếp của giá trị khoá đó.
  • Dòng bắt đầu bằng # là chú thích, archctl bỏ qua.
  • Tên chỉ gồm chữ, số, gạch dưới và gạch nối. Danh sách cách nhau bằng dấu phẩy: Order, Payment.
  • Cuối dòng có thể thêm hai chú thích: người đặt ra (@human hay @ai) và trạng thái (#draft, #proposed, #accepted, #locked). Không ghi thì mặc định là @human #accepted: thiếu chú thích thì luật có hiệu lực ngay, chặt hơn là lỏng.

Mười ba khai báo, từng cái một

component và external: đặt tên cho một khối mã

component gắn một tên với các file khớp mẫu đường dẫn sau at (nhiều mẫu thì cách nhau dấu phẩy). external là thư viện ngoài; sau at là tên gói như khi import.

component Web    at src/web/**                  @human #accepted
component Order  at src/order/**, lib/order/**  @human #locked
external  Stripe at "stripe"

Một file khớp hai component thì component khai trước thắng, và check cảnh báo "mẫu chồng nhau".

store: bảng dữ liệu thuộc về một component

Khai báo rằng chỉ component sau owned_by được chạm các bảng sau at. Đây là một lệnh cấm ngầm: component khác nhắc tên bảng đó trong chuỗi (câu SQL, tên collection) là vi phạm, trừ khi có allow viết tay tới store.

component Order at src/order/**
store OrderDB owned_by Order at "orders", "order_items"

allow và deny: ai được gọi ai

allow A -> B, C cho A gọi B và C. Một component đã có ít nhất một allow thì gọi sang chỗ không có trong danh sách là vi phạm. deny cấm thẳng. * ở phía nguồn nghĩa là "mọi component"; except (chỉ dùng với deny) liệt kê những nguồn được miễn.

component Web     at src/web/**
component Order   at src/order/**
component Payment at src/payment/**
external  Stripe  at "stripe"

allow Web     -> Order
allow Order   -> Payment
allow Payment -> Stripe
deny  * -> Stripe except Payment

Dòng cuối đọc là: mọi component, trừ Payment, không được đụng Stripe. Đích của allow/deny có thể là component, external, store hay nhóm api, nhưng không bao giờ là service.

api: một nhóm tên hàm bị theo dõi

Gom các tên hàm hay từ khoá mà archctl tìm thẳng trong mã (bỏ qua chú thích và chuỗi), rồi dùng nhóm đó làm đích của allow/deny. Hợp cho danh sách hàm nguy hiểm như strcpy.

component Parser at src/parser/**
component Legacy at src/legacy/**
api Unsafe at "strcpy", "gets", "sprintf"

deny  * -> Unsafe except Legacy

service và link: cái gì chạy ở đâu, nói chuyện với ai qua mạng

service là một đơn vị chạy (một container, một workload): from chỉ nguồn cấu hình (compose:, k8s:, dockerfile:, tf:, values:), runs liệt kê component chạy trong nó; cả hai tuỳ chọn, nhưng from phải đứng trước runs. link cho một service gọi service khác qua mạng; như allow, không có link là cấm. Service có không gian tên riêng, nên component Api và service Api cùng tồn tại được.

component Serve at src/serve/**
component Data  at src/data/**
service Api from compose:api runs Serve, Data
service Db  from compose:db
link Api -> Db

view: một góc nhìn để vẽ

Đặt tên cho một nhóm component. archctl export --view Checkout chỉ vẽ những component đó thay vì cả hệ thống. Không kiểm gì.

component Web     at src/web/**
component Order   at src/order/**
component Payment at src/payment/**
view Checkout: Order, Payment

flow: các bước của một luồng nghiệp vụ

Liệt kê các bước theo thứ tự. Thân khối nhận bốn dạng dòng: a -> b -> c, parallel: a, b, if <điều kiện>: a, on_fail(a): b (bước bù khi a hỏng). archctl kiểm mỗi bước có tồn tại trong mã; thứ tự thì chưa kiểm.

component Web   at src/web/**
component Order at src/order/**
flow PlaceOrder:                                   @human #accepted
  Web -> Order.reserveStock -> charge -> confirmOrder
  parallel: sendEmail, updateAnalytics
  if order.total > 0: charge
  on_fail(charge): releaseStock

Ba dạng bước: Web (tên component) không kiểm gì; Order.reserveStock kiểm reserveStock có và nằm trong Order, nên nên dùng dạng này; charge (tên trần) kiểm có ở đâu đó.

contract: lời hứa của một năng lực

Dòng đầu là Component.nănglực:. Thân khối chỉ nhận đúng bảy khoá: requires, ensures, errors, idempotent_by, latency, consistency, verify. archctl kiểm năng lực và các lỗi trong errors có tồn tại trong component; phần còn lại là văn xuôi, cần verify trỏ tới một bài test thật.

component Payment at src/payment/**
verify contract_test runs "npm run test:contract"
contract Payment.charge:                           @human #locked
  requires      order.status == RESERVED
  ensures       ok  => payment.status == CAPTURED
                err => không có tiền nào bị chuyển
  errors        Declined | Timeout
  idempotent_by orderId
  latency       p99 < 800ms
  consistency   strong
  verify        contract_test

boundary: một vùng cô lập lỗi

Dòng đầu là boundary Tên contains A, B:. Thân khối chỉ nhận đúng bảy khoá: isolation, propagate, contain, retry, timeout, compensate, verify. Khoá kiểm thật là contain: tên lỗi liệt kê ở đó mà xuất hiện ở component ngoài vùng là vi phạm (đó là vi phạm Web -> Timeout ở bước 3). compensate kiểm bước bù có tồn tại.

component Web     at src/web/**
component Order   at src/order/**
component Payment at src/payment/**
verify chaos_payment_down runs "npm run chaos -- payment-down"
boundary Checkout contains Order, Payment:         @human #accepted
  isolation   Payment.down => Order vẫn nhận đơn
  propagate   Declined -> user
  contain     Timeout, Unavailable
  timeout     toàn luồng < 3s
  compensate  charge.fail => releaseStock
  verify      chaos_payment_down

invariant và verify: điều luôn đúng, và lệnh chứng minh nó

invariant <loại> [phạm vi] <mệnh đề> verify <tên> ghi một điều phải luôn đúng. Loại là một trong data, state, money, time, access, algo; chỉ state được kiểm tĩnh (mỗi trạng thái phải có trong mã). verify <tên> runs "<lệnh>" gắn một tên với một lệnh shell; archctl verify chạy lệnh đó và ghi biên nhận.

component Order at src/order/**
verify property_test runs "npm run test:props"
invariant state [Order]  CREATED -> RESERVED -> PAID -> SHIPPED verify property_test
invariant data  [Order]  order.total == sum(items.price * items.qty) verify property_test

@ và # nằm trong dấu nháy kép được hiểu là nội dung lệnh, không phải chú thích.

Hai lỗi người mới hay gặp

Khoá lạ trong thân contract hay boundary là lỗi, không bị bỏ qua: gõ nhầm contian mà được nhận im lặng thì luật contain biến mất mà không ai hay.

component Order at src/order/**
boundary Checkout contains Order:
  contian  Timeout
⚠ cảnh báo:2: boundary `Checkout` không có verify, đây chỉ là lời hứa
✗ lỗi:3: không hiểu khoá `contian` trong boundary
  → có phải `contain`? Khoá hợp lệ: isolation, propagate, contain, retry, timeout, compensate, verify

except chỉ đi với deny. Một file có hai dòng component A, component B rồi đến dòng thứ ba allow A -> B except B cho:

✗ lỗi:3: `allow` không dùng được `except`
  → `except` chỉ có nghĩa với `deny`

Cả hai trường hợp, archctl parse trả mã thoát 2. Gõ lệnh này sau mỗi lần sửa tay file luật là cách nhanh nhất để biết mình viết đúng chưa.
